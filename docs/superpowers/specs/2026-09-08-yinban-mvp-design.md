# “银伴”医院智能陪诊导引机器人 MVP 设计规格

日期：2026-09-08  
状态：已完成对话设计审批，等待书面规格复核  
目标周期：7 天  
团队假设：1–2 人，以 Python/网页开发能力为主，缺少单片机经验  
硬件预算：人民币 500 元以内

## 1. 项目定义

“银伴”是面向老年人的医院智能陪诊与导引机器人比赛原型。它通过大字体界面、语音或按钮接收需求，回答预设医院流程问题，展示简化路线，并驱动 ESP32 巡线小车沿固定路线前往演示目的地。

本项目是用于验证交互、流程和软硬件联动的概念原型，不是可直接部署到真实医院的自主服务机器人。答辩和宣传材料必须明确区分“当前原型能力”和“未来产品规划”。

### 1.1 目标用户

- 不熟悉智能手机、自助机或复杂菜单的老年就医者。
- 看不清小字、听不清广播或在陌生医院中容易焦虑的用户。
- 需要科室方向、就医步骤或现场工作人员帮助的用户。

### 1.2 首周核心价值

- 让老人能够直接说出需求或点击一个大按钮。
- 把“去哪里”和“下一步做什么”放在同一交互中。
- 用实体小车演示从问询到导引的闭环。
- 在硬件或网络异常时仍能完成软件演示。

## 2. 范围与边界

### 2.1 P0 必须完成

- 高对比度、大字体的医院导引主页。
- “心内科、药房、厕所、人工求助”四个大按钮。
- 语音输入、文字输入和按钮输入。
- 约 15 条医院常见问法及同义表达。
- 本地医院科室与就医流程知识库。
- 简化路线节点和当前位置动画。
- 一条实体巡线路线：门诊大厅到心内科演示终点。
- 机器人出发、停止、继续、复位。
- 经典蓝牙 SPP 无线通信；USB 串口和车载启动按钮作为备用。
- 前方 15–20 厘米障碍停车。
- 障碍移除后恢复运行。
- 终点识别、自动停车和到达播报。
- 一键演示模式。
- 无硬件时的模拟机器人模式。
- 电机运行超时、通信中断和持续丢线停车保护。

### 2.2 P1 加分功能

只有 P0 稳定后才能实施：

- 第二条实体分支路线。
- 在线大模型处理未匹配问题。
- 求助时蜂鸣器和红色指示灯。
- 可视化事件日志。

### 2.3 明确不做

- ROS、SLAM、激光雷达和通用自主导航。
- 摄像头定位、视觉避障和人体跟随。
- 人脸、身份证、医保卡或 NFC 身份识别。
- 真实医院挂号、缴费、电子病历或电梯系统接入。
- 医疗诊断、药品推荐或个性化治疗建议。
- 机械臂、机器人头部和机载显示屏。
- 向真实医护人员发送求助信息。

人工求助在 MVP 中仅触发本地屏幕提示、声音或灯光，不得宣称已经通知医院工作人员。

## 3. 成功标准

完整演示流程应在 2 分钟内完成：

1. 用户说“我要去心内科”或点击心内科按钮。
2. 系统识别目的地并说明简化就医步骤。
3. 屏幕展示“门诊大厅→电梯口→心内科”。
4. 系统向小车发送出发指令。
5. 小车沿黑线低速行驶。
6. 放置障碍物后，小车自动停止并回传受阻状态。
7. 移除障碍物后，小车恢复行驶。
8. 小车识别终点、停车并回传到达状态。
9. 电脑播报到达提醒。

验收要求：

- 15 条预设问法全部正确匹配。
- 无网络时，按钮和文字输入仍能完成主流程。
- 一条实体路线能够连续稳定运行。
- 5 次障碍测试全部正确停车。
- 通信中断、持续丢线或运行超时后小车自动停车。
- 20 次完整彩排至少成功 18 次。
- 硬件故障时能在 30 秒内切换到模拟模式。

## 4. 技术方案

### 4.1 总体架构

    老人语音、文字或大按钮
              ↓
       浏览器老年友好界面
       ├─ 浏览器语音识别
       ├─ 浏览器语音合成
       ├─ 路线动画
       └─ 模拟机器人
              ↓ HTTP
       Python FastAPI 后端
       ├─ 规则意图识别
       ├─ 本地医院知识库
       ├─ 简化路线规划
       ├─ 可选 LLM 兜底
       └─ 机器人通信服务
              ↓ 串口
       Bluetooth SPP / USB
              ↓
          ESP32 状态机
       ├─ 五路红外巡线
       ├─ TB6612FNG 电机控制
       ├─ 超声波障碍检测
       ├─ 丢线与超时保护
       └─ 状态回传

### 4.2 技术栈

- 操作系统：Windows 10/11。
- 后端：Python 3.11、FastAPI、Uvicorn、Pydantic、pyserial。
- 前端：原生 HTML、CSS、JavaScript，避免引入 Node 构建链。
- 语音识别：Chrome/Edge 浏览器 Web Speech API；文字和按钮为强制兜底。
- 语音合成：浏览器 speechSynthesis。
- 数据：JSON 文件，不使用数据库。
- 固件：Arduino IDE、Arduino C++。
- 通信：开发阶段使用 USB 串口；演示阶段优先使用经典蓝牙 SPP 虚拟串口。
- 测试：pytest；硬件未到时使用模拟串口服务。

### 4.3 关键取舍

- 固定问题先走规则匹配，不让在线 LLM 成为关键依赖。
- 前端不用 React/Vue，减少安装和构建故障。
- 后端不使用数据库，医院数据和路线都放在可读 JSON 文件中。
- 只保证一条实体路线，其他目的地可在软件中展示。
- 使用原版 ESP32-WROOM-32；需要经典蓝牙 SPP 时不采用 C3、S2 或 S3。
- 采用低速巡线和状态机，不追求竞速 PID 参数。

## 5. 软件组件

### 5.1 Web UI

职责：

- 提供四个大按钮、语音按钮和文字输入。
- 展示识别文本、机器人回答、路线节点和当前状态。
- 调用浏览器语音识别和语音合成。
- 提供演示、停止、复位和模拟模式控制。

界面要求：

- 默认字号不小于 24 px，主要按钮文字不小于 28 px。
- 高对比度配色，避免仅依靠红绿区分状态。
- 每屏只展示一个主要任务。
- 始终显示“停止导引”和“人工求助”。

### 5.2 意图识别

主流程使用确定性匹配：

- navigate：心内科、药房、厕所、检验科等目的地。
- process：挂号、报到、候诊、检查、缴费、取药。
- help：不舒服、迷路、找工作人员、需要帮助。
- stop：停止、别走了、停下。
- unknown：无法识别。

匹配顺序：

1. 紧急和停止关键词。
2. 目的地词典及同义词。
3. 就医流程词典。
4. 可选在线 LLM。
5. 友好澄清，并展示大按钮。

### 5.3 医院知识库

hospital.json 保存：

- 科室名称、别名、楼层和位置描述。
- 挂号到取药的简化流程。
- 厕所、电梯、服务台等公共设施。
- 非医疗性质的安全提示。

系统不得生成诊断结论。涉及症状、用药或紧急不适时，回答应引导用户联系医护人员或急救服务。

### 5.4 路线服务

routes.json 定义地图节点、连接关系、展示路线和机器人路线编号。

第一版实际路线：

- 起点：门诊大厅。
- 中间节点：3 号电梯口。
- 终点：心内科演示区。
- 机器人路线编号：CARDIOLOGY。

软件可以为其他地点展示路线，但在未实现对应实体线路前不得向小车发送不受支持的路线编号。

### 5.5 机器人通信服务

职责：

- 打开和关闭 Windows 串口。
- 发送单行文本指令。
- 异步读取状态。
- 通过状态接口向 Web UI 提供最新硬件状态，前端每 500 毫秒轮询一次。
- 串口不可用时自动进入模拟模式，但必须在界面上明确标识。

通信协议：

    电脑 → 小车
    PING
    START:CARDIOLOGY
    STOP
    RESUME
    RESET

    小车 → 电脑
    READY
    MOVING
    BLOCKED:18
    LINE_LOST
    ARRIVED:CARDIOLOGY
    ERROR:SENSOR

所有消息以换行结束。未知指令返回 ERROR:UNKNOWN_COMMAND。

### 5.6 ESP32 固件

状态：

- IDLE：等待任务。
- FOLLOWING：巡线。
- BLOCKED：检测到障碍并停车。
- LINE_LOST：持续丢线并停车。
- ARRIVED：到达终点。
- ERROR：传感器或内部故障。

安全规则：

- STOP 在所有状态下拥有最高优先级。
- 启动后超过设定最长时长仍未到达则停车。
- 丢线超过设定时间后停车，不盲目持续前进。
- 超声波读数连续多次低于阈值才判定障碍，避免单次噪声。
- 只有在 BLOCKED 状态且障碍连续消失后才自动恢复。

## 7. API 草案

### POST /api/dialogue

输入：

    {"text": "我要去心内科"}

输出：

    {
      "intent": "navigate",
      "destination": "cardiology",
      "answer": "心内科位于三楼，请跟随导引路线。",
      "route": ["门诊大厅", "3号电梯口", "心内科"],
      "robotRouteId": "CARDIOLOGY"
    }

### POST /api/robot/start

输入：

    {"routeId": "CARDIOLOGY"}

输出：

    {"accepted": true, "mode": "hardware"}

### POST /api/robot/stop

立即发送 STOP，不等待其他任务完成。

### GET /api/robot/status

输出当前模式、连接状态、运动状态、障碍距离和最后一条错误信息。

## 10. 测试策略

### 10.1 自动测试

- 意图识别：每个意图覆盖标准说法、同义说法和容易误判的说法。
- 路线规划：验证合法路线、未知目的地和不支持的实体路线。
- 通信协议：验证拆包、未知消息、断线和模拟模式。
- API：验证正常输入、空输入、超长输入和硬件不可用。

### 10.2 硬件测试

- 左右轮方向和 PWM 速度。
- 五路传感器的黑白阈值。
- 直线、缓弯和终点标记。
- 障碍出现、持续和移除。
- 运行中 STOP。
- 蓝牙断开、USB 拔出和电池电量降低。

### 10.3 演示回归

Day 7 每次彩排记录：

- 语音是否识别。
- 路线是否正确。
- 小车是否启动。
- 障碍是否停车。
- 是否到达。
- 总耗时和失败原因。

同一种故障出现两次后停止增加功能，优先修复或启用备用方案。

## 11. 风险与降级策略

| 风险 | 影响 | 处理 |
|---|---|---|
| 物流延迟 | 无法及时组装 | Day 3 前完成模拟机器人；保留备用视频 |
| 语音识别受噪声影响 | 无法理解用户 | 同屏显示大按钮和文字输入 |
| 蓝牙配对失败 | 无法无线控制 | 使用 USB 串口或小车本地启动 |
| 巡线不稳定 | 实体演示失败 | 降低速度、放大转弯半径、只保留一条路线 |
| 传感器电平不兼容 | 损坏 ESP32 | 下单前确认 3.3V 兼容；首次上电前测量 |
| 电机干扰导致重启 | 演示中断 | 固定接线、使用配套电源、逻辑与电机共地 |
| 在线 API 不可用 | 问答失败 | P0 全部使用本地规则和 JSON |
| 项目被质疑“假自主” | 可信度下降 | 明确称为固定环境概念验证，不冒充 SLAM |

## 12. 数据、医疗和展示规范

- MVP 不采集或保存真实患者姓名、身份证号、病历、联系方式和人脸。
- 日志只保存匿名测试文本和机器人状态。
- 系统不提供诊断、处方或药物剂量建议。
- 用户表达严重不适时，界面提示立即联系现场医护或拨打急救电话。
- 演示中不伪造医院接口、医护通知或定位精度。
- 使用第三方开源代码前检查许可证并保留来源说明。

## 13. 参考实现的使用方式

- RoboHospitalGuide：仅参考预设地图、GUI 与硬件抽象的模块思想，不采用其树莓派、Qt6、人脸识别和四驱实现。
- voice-controlled-hospital-robot：仅参考语音输入到意图和命令执行的分层方式。
- hospital-voice-robot-c：仅参考 ASR、问答和 TTS 的链路，不部署 FunASR 与 CosyVoice。
- ESP32-Line-Follower-Car：优先参考其五路巡线、状态机和 PD 控制；按实际采购硬件重写引脚和安全逻辑。

这些仓库是参考资料，不是可直接交付的成熟依赖。项目应保留自己的目录、数据、交互流程和软硬件协议。

## 14. 实施入口

书面规格通过用户复核后，下一阶段应：

1. 编写逐任务实施计划。
2. 初始化代码目录和运行环境。
3. 优先实现无需硬件的端到端软件主流程。
4. 使用模拟机器人完成接口测试。
5. 硬件到货后实现固件和真实串口适配。
