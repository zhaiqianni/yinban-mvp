## 1. 项目目标与边界

项目名称为“银伴”，目标是制作一套面向老年就医者的医院智能陪诊导引原型。项目采用网页软件与实体巡线小车结合的演示方式：

1. 老年用户可以通过语音、文字或大按钮询问科室位置和就医流程。
2. 网页显示医院逻辑地图、楼层变化和多目的地顺序。
3. 对已经配置的实体路线，网页可以向 ESP32 小车发送开始、停止、继续和复位命令。
4. 小车在受控场地内沿黑色胶带低速巡线，到达宽黑色终点条后停车。
5. 当前不宣称小车能在真实医院内完成 SLAM、自主建图、自由避障、自动乘电梯或陌生环境导航。

用户已确认的总体约束：

- 参赛作品以“能稳定演示的原型”为目标。
- 更倾向于实物演示与网页结合。
- 硬件预算控制在 500 元以内。
- 当前没有很大的测试场地，因此测试路线应尽量短而可验证。
- 第一版只做一条实体路线，其他路线可以由网页模拟。

## 3. 电脑与网页通信设计

既定通信链路为：

```text
浏览器网页
    ↓ HTTP
本地 FastAPI/Python 后端
    ↓ pyserial
USB COM 口或蓝牙虚拟 COM 口
    ↓
ESP32 小车
    ↓
五路循迹传感器、电机和安全状态机
```

网页不直接使用 Web Bluetooth。ESP32 使用经典蓝牙 SPP，Windows 配对后将其显示为虚拟 COM 口，Python 后端仍使用 `pyserial`。这样可以先用 USB 调通，再仅替换 COM 口切换至蓝牙。

现有后端通信文件：

- `app/services/robot_link.py`
- `app/services/robot_protocol.py`
- `app/config.py`

现有命令协议：

```text
PING
START:CARDIOLOGY
STOP
RESUME
RESET
```

现有状态协议：

```text
READY
MOVING
LINE_LOST
BLOCKED:<距离厘米>
ARRIVED:CARDIOLOGY
ERROR:<错误原因>
```

后端硬件模式预期使用的环境变量：

```powershell
$env:YINBAN_MODE = "hardware"
$env:YINBAN_ROBOT_PORT = "COM5"
$env:YINBAN_ROBOT_BAUD = "115200"
```

其中 `COM5` 是当前 USB CH340 串口。蓝牙调通后应替换为 Windows 为 `YINBAN_ROBOT` 分配的蓝牙输出 COM 口。

## 6. 已使用的诊断程序

当前已烧录并实测的是：

```text
firmware/diagnostics/c001_line_follow_diagnostic/c001_line_follow_diagnostic.ino
```

该程序主要安全参数：

- 上电或复位后等待 8 秒再启动。
- 基础 PWM：90/255，约 35%。
- 单次最长运行时间：10 秒。
- 丢线后立即停止驱动，持续丢线 150 毫秒后结束测试。
- 五路传感器同时检测黑色时，按宽黑终点条处理。
- GPIO25 按钮可以停止。
- 每次上电只运行一次，不会自动重复启动。

可能输出的停止原因包括：

```text
STOP:WIDE_BLACK_MARK
STOP:LINE_LOST
STOP:TIME_LIMIT
STOP:BUTTON
STOP:NO_LINE_AT_START
```

## 8. 下一次必须进行的测试

### 8.1 短距离终点独立测试

目的：把“宽黑条停车”和“10 秒超时停车”区分开。

操作步骤：

1. 将小车前方蓝色五路探头放在距离横向终点条 20～30 厘米的位置。
2. 中间探头对准纵向黑线。
3. 按复位键。
4. 等待 8 秒启动保护结束。
5. 小车应在开始移动后的约 1～3 秒内到达横线并停车。
6. 最好保持 USB 串口监视器连接，直接读取停止原因。

通过标准：

- 串口明确显示 `STOP:WIDE_BLACK_MARK`。
- 蓝色五路探头停在横向黑条上。
- 停止时间明显短于 10 秒。

如果只看到车停下而没有串口原因，证据仍不完整。

### 8.2 后续测试顺序

终点确认后依次测试：

1. **丢线停车**：在前方设置 5～8 厘米断线，确认不会继续盲目前进，并输出 `STOP:LINE_LOST`。
2. **本地停止按钮**：运行中按 GPIO25，确认电机立即停止且不会自动重启。
3. **左弯和右弯**：使用半径不小于约两倍车身长度的缓弯，不测试直角弯。
4. **障碍停车**：在最终固件整合并确认避障引脚后进行；检测到障碍应停车并上报 `BLOCKED`。
5. **重复测试**：完整路线连续运行至少 10 次，目标至少 9 次无需扶正或重启。

## 9. 最终固件的关键问题

现有文件：

```text
firmware/yinban_car/yinban_car.ino
```

不能直接烧录到当前小车。该文件仍使用旧方案：

- 使用 `STBY`、`PWMA`、`PWMB` 等旧电机驱动假设。
- 循迹引脚仍是旧的 `32, 33, 34, 35, 39`。
- 超声波占用 `18, 19`，与当前五路循迹接线冲突。
- 电机方向和当前实测结果不一致。

下一阶段必须将已经验证的诊断程序引脚和控制逻辑合并到最终固件，而不是直接烧录旧文件。

最终固件至少应具有以下状态：

```text
IDLE       上电安全停止，等待 START
MOVING     低速巡线
BLOCKED    发现障碍并停车
PAUSED     收到 STOP 后保持停车
LINE_LOST  丢线停车
ARRIVED    识别终点后停车
ERROR      超时、传感器异常或命令异常
```

最终固件必须满足：

- 上电不自行运动。
- 只有收到 `START:CARDIOLOGY` 后才启动。
- USB 串口和经典蓝牙 SPP 使用同一套命令解析器。
- 收到 `STOP` 后立即关闭两侧电机。
- 终点上报 `ARRIVED:CARDIOLOGY`。
- 丢线、超时、断连和传感器异常默认停车。
- 建议增加通信心跳：运动期间如果连续约 1～2 秒没有收到电脑心跳，执行安全停车。

## 10. 从当前状态到网页控制小车的剩余步骤

### 步骤 1：完成当前硬件安全测试

至少确认终点、丢线、本地停止和缓弯。

### 步骤 2：重构并烧录最终固件

将当前已验证的五路传感器、电机引脚和巡线算法合并到 `firmware/yinban_car/yinban_car.ino`，再加入命令状态机和状态回传。

### 步骤 3：使用 USB COM5 直接测试文本命令

逐项验证：

```text
PING                 → READY
START:CARDIOLOGY     → MOVING
STOP                 → 停车并返回安全状态
RESET                → READY
到达横向终点条       → ARRIVED:CARDIOLOGY
```

在这一阶段不要先接网页，以便区分是固件问题还是网页问题。

### 步骤 4：让 Python 后端连接 COM5

设置硬件模式和串口后启动本地服务。网页点击“开始引导”时，后端应发送 `START:CARDIOLOGY`；网页应轮询并显示小车状态。

### 步骤 5：进行网页端到实体车的完整闭环测试

标准流程：

1. 网页输入“我想去心内科”。
2. 网页显示门诊大厅、一楼 3 号电梯口、乘梯和三楼心内科路线。
3. 点击“开始引导”。
4. 小车开始巡线。
5. 小车到达横向终点条并上报 `ARRIVED:CARDIOLOGY`。
6. 网页显示小车已到达电梯口。
7. 网页继续模拟乘梯和三楼路线。

### 步骤 6：启用 ESP32 内置经典蓝牙

最终固件调用 `SerialBT.begin("YINBAN_ROBOT")`。Windows 配对后找到对应的输出虚拟 COM 口，先用串口工具验证命令，再将 `YINBAN_ROBOT_PORT` 从 `COM5` 改为蓝牙 COM 口。

### 步骤 7：故障和降级测试

- 网页 STOP 必须立即停车。
- 蓝牙断开或心跳超时必须停车。
- 蓝牙失败时可改用 USB。
- USB 也失败时网页切换为模拟机器人，实体车不继续运动。

## 11. 实体路线如何设置

当前小车不是按照网页坐标进行导航。第一版路线由地面胶带决定：

- 白色或浅色平整地面。
- 哑光黑色胶带作为连续路线。
- 弯道使用大圆弧，不使用直角。
- 终点使用横跨五路探头的横向宽黑条。
- 当前只配置一条实体路线 `CARDIOLOGY`，实际含义是“门诊大厅至一楼 3 号电梯口”。

电脑只发送路线编号和控制命令，ESP32 根据传感器自行修正左右电机。若未来要在实体岔路中选择多个目的地，需要增加路口标记识别、编码标签或其他定位方案；当前比赛版本不做这一扩展。

## 13. 不应误判或夸大的事项

- 目前尚未证明宽黑条终点识别已经通过，因为现有视频与 10 秒超时重合。
- 当前已经证明的是直线基础循迹，而不是复杂医院自主导航。
