# 银伴蓝牙断线自动恢复设计

## 背景与根因

当前真实硬件模式使用 Windows 经典蓝牙 SPP 虚拟串口 `COM6`。小车突然断电或蓝牙链路波动后，Windows 可能暂时保留 COM6 设备节点，但实际端口不可打开或写入长期阻塞。

现有后端存在三个耦合问题：

1. 串口只设置读取超时，没有设置写入超时。
2. 串口写入与状态快照共用同一把锁；写入阻塞时，`/api/robot/status` 也会阻塞。
3. 串口只在服务启动时连接一次，断线后不会自动重新打开。

前端每 500 毫秒用 `setInterval` 发起一次状态请求，没有请求超时和在途请求限制。后端阻塞后，浏览器会积压请求并把机器人断线误显示为“后端连接失败”。

## 目标

- 小车断电或蓝牙短暂中断时，网页服务继续响应。
- 网页明确显示“机器人离线，正在重连”，而不是误报整个后端离线。
- Windows 再次提供指定 COM 口后，后端自动重连，无需重启服务。
- 串口读写异常不会长期占用状态锁。
- 自动重连期间，启动、继续和复位指令明确失败，不能误报成功。
- 保留 ESP32 端 1.5 秒通信看门狗作为最终电机安全保护。

## 非目标与边界

- 应用不会修改 Windows 蓝牙配对、驱动或管理员级设备配置。
- 如果 Windows 完全删除蓝牙串口且不再重新创建，应用只能持续报告并重试，不能代替系统重新配对。
- 本次不修改循迹、超声波、电机和路线决策算法。
- 本次不引入额外守护进程、Windows 服务或第三方消息中间件。

## 方案比较

### 方案 A：发生故障后自动重启整个 Web 服务

实现简单，但会中断所有网页请求，可能丢失当前路线状态，并且无法区分端口短暂波动与真正的服务故障。不采用。

### 方案 B：后端内部使用可恢复串口连接，前端使用有界轮询

Web 服务始终在线，串口连接独立恢复；状态接口不依赖正在执行的串口 I/O。改动集中在现有 `SerialRobotLink` 和状态轮询代码，符合当前单机比赛原型。采用此方案。

### 方案 C：新增独立硬件代理进程或 Windows 服务

隔离性最好，但部署、调试和比赛现场运维复杂度过高，超出当前 MVP 范围。不采用。

## 后端设计

### 1. 锁与状态隔离

`SerialRobotLink` 使用三类同步对象：

- 状态锁：只保护串口引用和 `RobotSnapshot`，任何串口打开、关闭、读取或写入都不得在持有状态锁时执行。
- 写入锁：只负责串行化 `PING`、`START`、`STOP`、`RESUME` 和 `RESET` 写入。
- 连接尝试锁：保证同一时间最多只有一次端口打开或重连尝试。

`status()` 只复制并返回快照，因此即使 Windows 串口调用卡顿，状态接口也必须立即返回。

### 2. 串口超时

打开端口时统一设置：

- `timeout=0.2` 秒，用于读取。
- `write_timeout=0.5` 秒，用于写入。

写入超时、读取异常或句柄失效时，连接立即标记为断开；失败的 `STOP` 不能返回成功。

### 3. 后台重连

`connect()` 启动常驻后台线程，不再要求首次打开 COM 口成功后 Web 服务才能启动。

后台线程规则：

1. 无有效串口时，每 2 秒尝试打开配置的端口。
2. 打开操作不持有状态锁，因此 Windows 打开端口较慢时不影响状态接口。
3. 打开成功后发送 `PING`，将快照更新为 `connected=true`、`state=IDLE`。
4. 读取到 ESP32 事件时更新快照。
5. 发生读取或写入异常时，只关闭发生故障的当前句柄，快照改为 `connected=false`，随后回到重连循环。
6. `close()` 先设置停止事件并关闭串口，再等待后台线程结束，避免退出时被阻塞读取拖住。

### 4. 模式语义

- `YINBAN_MODE=hardware` 且配置了端口时，始终返回可恢复的 `SerialRobotLink`；首次连接失败不得自动替换为模拟机器人。
- `YINBAN_MODE=simulation` 时继续使用 `MockRobot`。
- 未配置端口时，硬件模式返回明确的离线错误，不静默伪装成真实连接。

### 5. 断线期间的命令

- `START`、`RESUME`、`RESET`：立即拒绝，并返回“机器人离线，正在重连”。
- `STOP`：尝试写入；无法发送时明确返回失败。ESP32 已有通信看门狗，会在心跳停止后约 1.5 秒本地停车。
- 状态接口持续返回 HTTP 200，并通过 `connected=false` 与 `error` 描述机器人链路状态。

## 前端设计

### 1. 有界请求

通用 `api()` 请求增加 3 秒超时。超时后取消该请求，避免浏览器连接长期占用。

### 2. 非重叠轮询

取消固定 `setInterval`，改为一次请求结束后再用 `setTimeout` 安排下一次：

- 后端正常时每 500 毫秒轮询。
- 后端不可达时每 2 秒重试。
- 任意时刻最多存在一个状态请求。

### 3. 状态文案

- HTTP 正常且 `connected=true`：显示“真实硬件模式”。
- HTTP 正常且 `connected=false`：显示“真实硬件模式 · 正在重连”，机器人状态显示“机器人离线”。
- HTTP 请求本身失败或超时：才显示“后端连接失败”。

机器人离线期间禁用“开始实体导引”和“继续”，但保留路线问询、地图和模拟内容展示。

## 测试设计

### 自动化测试

使用可控的假串口覆盖：

1. 写入阻塞或超时时，`status()` 在 100 毫秒内返回。
2. 初次打开端口失败时，控制器保持硬件模式并报告正在重连，而不是切换模拟模式。
3. 前两次连接失败、第三次成功时，控制器自动恢复为 `connected=true`。
4. 读取异常和写入异常都能关闭失效句柄并进入重连。
5. 断线期间的控制命令返回失败且不误报成功。
6. 多线程同时请求状态与命令时，不发生死锁或重复打开端口。
7. `close()` 能结束后台线程并释放串口。

### 实机验收

1. 真实硬件模式启动并确认 COM6 连接。
2. 保持网页打开，关闭小车电源。
3. 1 秒内网页仍能响应，并显示“机器人离线，正在重连”。
4. 等待 5 秒，确认服务进程和网页仍正常。
5. 重新打开小车电源；Windows 再次提供 COM6 后，网页应在 10 秒内恢复“真实硬件模式”。
6. 无需重启后端，发送一次开始与停止命令并由用户确认车轮响应。
7. 连续完成三轮断电、上电和重连，均不得出现状态接口卡死或请求堆积。

## 验收结论

只有同时满足以下条件，才能称为“永久恢复”已完成：

- 断电不会拖死 Web 后端。
- 状态接口在串口异常时仍可及时响应。
- COM 口恢复后能够自动重新连接。
- 网页区分机器人离线与后端离线。
- 重连后实体开始、停止命令可用。
- 三轮实机断电恢复测试全部通过。
